# 三档压缩与性能验收

三档同时控制磁盘表示和送入模型的任务上下文。数据模式给出完整获准表示，平衡模式消除重复，高压缩进一步缩短可安全表达的内容。三档持有相同的权威事实和可回查的获准原文。用户要求准确率不下降，因此紧凑模板按任务类型、模型和宿主验证后才启用；没有通过验证的场景发送已验证的保真表示。下列压缩参数是首轮对照的设计起点。[权威数据与事务](authority.md) · [产品验收场景](../product/acceptance.md)

## 档位如何工作

在 CLI 运行 `bmem config set profile balanced`，或在本机 Web 配置中选择同名档位。两处读取同一个配置版本。每个已存对象自描述实际编码，允许旧数据和新数据在切换期间共存。

| 工作负载 | 数据模式 `data` | 平衡 `balanced` | 高压缩 `high` |
|---|---|---|---|
| 适用场景 | 检索调优、频繁回读和基准比对 | 日常声明、普通对话与工具回执，建议初始默认 | 长期积累的大量可压缩原文，愿意用后台 CPU 换磁盘 |
| 证据与附件 | 保管允许留存的原始字节，直接按范围读取 | 对达到 1 KiB 的可压缩正文比较 Zstd 3 级编码和原长，只保存较小表示 | 新写沿用平衡策略。后台对已封存且近期无读取的对象尝试 9 级，只在新表示更小时切换。前台不用等重压缩 |
| 短记录、已压缩媒体与不可压缩块 | 原样保存 | 短记录直接保存，已知压缩格式跳过试压 | 同平衡。保留已有最小可读表示，后台可跳过无收益的对象类型 |
| 查当前事实、历史、撤回状态 | SQLite 中的类型化列和必要索引直接查询 | 同数据模式 | 同数据模式 |
| 任务上下文 | 提供这次查询选定、已获准、在预算内的完整工作集。各事件保留完整字段名、原文窗口和独立来源 | 保留相同工作集。共同的项目、工件、时间条件只写一次，以稳定引用代替同一修订的重复正文；不同角色和独立根逐一列出 | 已验证的任务类型使用紧凑证据包，保留结论、适用条件、关键原句或结构化结果、根来源和可展开句柄。原文问题、歧义和缺证时自动展开或回退 |
| 证据召回与授权 | 固定分词、BM25、候选上限、模型、目的地及授权快照作对照 | 相同检索语义，减少重复字段 | 相同候选与顺序，按证据充分性裁剪各项表达。三档均默认关闭向量检索，启用向量另行评测 |
| CPU 与空间 | 优先降低编码开销，正文占用较大 | 单对象编码，压缩上下文按任务复用 | 单个低优先级重打包任务，前台写积压时让出。受活动库、暂存和备份共同可用空间限制 |

短证据可内联在 SQLite。大对象保存为若干可独立解码的有界帧，并索引每帧的原始字节范围；例如从 256 KiB 的逻辑块开始测试。原始的字段路径或字符起止始终相对同一来源版本。物理随机读取可以用 UTF-8 字节偏移，映射时保留合法字符边界。这样调查报告末尾的一条工具回执时，只展开覆盖该片段的块。Zstandard 的级别允许在压缩速度、内存和体积间取舍；独立帧的取舍属于 bmem 的存储设计。[Zstandard 官方说明](https://facebook.github.io/zstd/) · [RFC 8878 帧格式](https://www.rfc-editor.org/rfc/rfc8878.html#section-3.1)

## 存储、搜索与送给助手的内容

1. **物理存储。** 对入口移除凭据后允许保存的证据字节计算摘要，记录长度、编码版本、块位置和每个来源引用。可在同一保管与清理域内复用字节相同的块。不同账号对象及相同事实的独立证言仍有各自的来源、修订、权限和出处。两个助手转述同一事件仍指向同一证据根。外部读取只凭授权的稳定句柄进入。
2. **全文索引。** 三档共用普通 FTS5、相同的分词与 `detail=full`，索引有效版本，候选回到权威层按当前权限补读。删除词位会影响短语和 NEAR 查询。免除 FTS 自带的正文副本可以另试 contentless-delete，准入须覆盖编辑、删除和重建后的排序。在本机 SQLite 3.53.1 的三行夹具中，普通表与 contentless-delete 表初始得到相同 BM25 分数，删除一条命中后均只返回同一剩余行，但该行在两表中的分数分别约为 −0.000000907 和 −0.4963。该单例观察到分值差异，须用多候选任务再验证排名与交付。首发按普通索引把此副本计入实际磁盘和清理范围。[SQLite FTS5 无正文可删除表](https://www.sqlite.org/fts5.html#contentless_delete_tables) · [SQLite FTS5 detail](https://www.sqlite.org/fts5.html#the_detail_option)
3. **模型上下文。** 先按授权、时间、来源、任务选择相同工作集，然后按档位序列化。数据模式的“完整”限定在本次允许且相关的工作集内。原文带有来源角色，重复引用保留独立出处、否定、条件、有效时间、修订及明确的成功或失败状态。宿主的声明预算和任务证据预算分别处理。Zstd 文件字节不能代表模型接收的 token 数。研究中按消息检索在 438 题里有 369 题找全金标会话，实际送出的最高分消息覆盖各金标会话标注的只有 203 题，因此必须检验所送证据能否支持结论。[研究中的证据粒度回放](../../../research/reassessment-2026-11/local-evidence.md)

### 同一条接手任务，三种实际表示

以下只展示任务包正文。另随包提供当前可用声明修订及适用条件。所选材料都是同一项目、同一工件，时间为合成的当地时间。E8、E9 是本接收域当前可展开的示例句柄。真实模型仅收到该路由和用途获准的材料。

| 档位 | 模型实际能读到的示例 |
|---|---|
| 数据模式 | 事件 E8，项目溪桥，工件 import@3，10:00，发言者为操作者，普通对话原文“准备复验解析与入库”。事件 E9，项目溪桥，工件 import@3，10:02，发言者为工具，执行回执原文“解析通过，入库仍超时”。任务指向 E8、E9。 |
| 平衡 | 溪桥 / import@3。E8〔10:00，操作者，计划〕“准备复验解析与入库”。E9〔10:02，工具，执行结果〕“解析通过，入库仍超时”。 |
| 高压缩 | 溪桥 / import@3。10:00 计划复验解析、入库〔操作者 E8〕。10:02 解析已通过、入库仍超时〔工具 E9〕。 |

按上表正文的 UTF-8 字节计，这三个示例分别为 285、166、131 B。宿主模板、分词器与补读轮次会改变实际 token 开销，验收按真实模型的计量记录。上述高档示例只适用于已通过验证的“接手当前故障”读法。用户询问逐字表述时直接给原句。若代码片段、否定、前置条件、例外、数字单位或冲突出处无法用已验证模板表达，服务在发送前装入必需原文。宿主不能继续补读时，先行展开必要证据；若仍无法证明充分，按平衡或数据表示组包。重新鉴权失败则剔除不可读材料、重新判断能否回答；证据预算不足则标明缺口或暂缓必需快照的装入。原句受限的共享声明仅提供其独立获准字段。记录实际使用档位、回退原因与每次实际补读，不能用跨路由句柄补齐无权原文。

**切档与恢复。** 保存配置后，新对象按新策略入库。已有对象可后台分批重打包，按对象记录目标档、已处理字节、编码失败和待处理量。先写临时新表示并逐块解码校验长度、原始摘要，再由短事务换物理引用。档位切换只改变随后新组装的任务包，已发送版本留在投递回执中。保留当前读者和受管备份仍引用的旧表示。崩溃或磁盘不足时继续用最后成功的表示，重启可按对象恢复；需要恢复原始表示时以同一流程解码。压缩作业开始和提交时复核对象仍应保管。遇到撤回立即阻断读取，废弃尚未发布的编码结果，并将新旧块、缓存、索引和受管备份纳入同一清理单。有独立授权来源引用同一物理块时，撤掉本来源引用并分别展示剩余保管依据。[备份、清理与恢复](operations.md)

## 本机无损编码小实验

在 macOS arm64、Python 3.12.13、python-zstandard 0.25.0 / libzstd 1.5.7 上实测。2,048 件独立合成对象包含 512 条短回执、512 件每件 8 KiB 的确定性高熵数据、1,024 件带独立标签的中英日志。逐件编码、每件单帧，输入与工作集都在内存中，相同顺序运行 5 次。耗时含 Python 循环、分配和库调用。

| 编码策略 | 载荷总字节 | 原长占比 | 全批编码 / 解码中位耗时 |
|---|---:|---:|---|
| 原始字节 | 8,493,674 | 100% | 直接读取，未测耗时 |
| Zstd 3，短项和变大项保留原样 | 4,921,668 | 57.95% | 8.7 ms / 3.8 ms |
| Zstd 9，同样回退到较小表示 | 4,906,517 | 57.77% | 30.2 ms / 3.4 ms |

两档均逐对象复原相同字节。9 级相对 3 级在这批数据上仅再省 15,151 B，编码耗时约 3.5 倍。这支持在冷数据上试高档，并按实际收益决定是否重编码。载荷不含 SQLite、WAL、元数据、块引用、缓存及备份，未运行模型、检索和宿主。三平台的应用吞吐、RSS 与准确率仍须按下节验收。

<details>
<summary>复现输入与计量</summary>

下列 Python 脚本仅用于复现实验，在已有 `zstandard==0.25.0` 的环境中运行。V2 的原生发行物设计为内嵌所需解码器。原始对象按生成顺序连接的 SHA-256 为 `8e08853455e74f8156797489c70fcf34456f917fccad7b69905b6e04aaabb160`。

```python
from hashlib import sha256, shake_256
from statistics import median
from time import perf_counter
import zstandard as zstd

def evidence(i):
    seed = str(i).encode()
    if i % 4 == 0:
        return f"run={i} 解析通过，写入超时。".encode()
    if i % 4 == 1:
        return shake_256(seed).digest(8192)
    return "".join(
        f"task={i} step={j} tag={sha256(f'{i}/{j}'.encode()).hexdigest()[:12]} 解析通过，写入超时。\n"
        for j in range(64)
    ).encode()

objects = [evidence(i) for i in range(2048)]
print("raw", sum(map(len, objects)), sha256(b"".join(objects)).hexdigest())
for level in (3, 9):
    codec = zstd.ZstdCompressor(level=level)
    reader = zstd.ZstdDecompressor()
    writes, reads = [], []
    for _ in range(5):
        start = perf_counter()
        packed = []
        for raw in objects:
            data = codec.compress(raw) if len(raw) >= 1024 else raw
            packed.append((True, data) if len(data) < len(raw) else (False, raw))
        writes.append(perf_counter() - start)
        start = perf_counter()
        decoded = [reader.decompress(data) if coded else data for coded, data in packed]
        reads.append(perf_counter() - start)
        assert decoded == objects
    print(level, sum(len(data) for _, data in packed),
          round(median(writes)*1000, 1), round(median(reads)*1000, 1))
```

</details>

## 实现后如何验收

| 检查 | 固定的输入及对照 | 放行与退回 |
|---|---|---|
| 权威状态与随机补读 | 用同一授权事件流、固定版本的提案重放三档，含中英混排、中文多字节边界、空值、代码/缩进、已压缩附件、重复来源、未来/已撤回修订 | 逐件字节与摘要、抽取字段、修订关系、当前和双时态查询、允许/禁止补读应一致。撤回后新旧表示均禁读，合法对照仍可查 |
| 检索与上下文 | 固定词法、候选预算、授权和查询时点，稳定次序打破同分。只切磁盘编码时核对最终输入字节；另切上下文策略，核对候选 ID 与顺序、各事实的主体、值、条件、时间、来源、否定、待证与实际装入修订，并逐柄回读 | 物理编码实验要求输入相同。上下文实验要求同任务的关键事实与必要证据逐条等价，限制信息零新增披露。某字段或证据不能保真即回退较完整表示并重测 |
| 真实任务准确率 | Claude Code 与 Codex 各用相同获准路由，从普通对话、实际工具回执、一次性条件、旧事实及拒答样本接力。固定模型版本、输入预算、评分器及环境，重复运行并按任务族配对 | 在数据模式基线上预注册任务族、金标及主指标。比较提炼准确性、证据充分、接手成功、合理拒答与错用。报告配对得失及分母，对准确率差按任务族成簇估计单侧 95% 下界。正式启用紧凑模式要求主指标下界 ≥ 0、关键切片的确定性断言全过；样本量不足或已有可复现退化时回退并增加留出样本。有限样本的结论限定于所测模型、宿主和任务 |
| 资源与交互 | 在三系统各用固定生成种子与三档语料量（建议首轮 1 千、10 万、100 万个来源版本），另记原文总字节及各类长度分布。冷启动与热态分别执行批量回填、单条声明、即时读取、词法/原文补读、真实提炼、重打包时前台查询、空目录恢复 | 记录 CLI 启动与请求 p50/p95/p99、确认摄入条/s、提炼积压年龄、CPU 时间、空闲/峰值内存、解码读放大、每成功任务 token。除首包外，累计所有自动展开、后续补读、重试及回退实际进入模型的 token，单列输出 token、调用数和未完成任务。单列服务、浏览器与推理进程。按整库、WAL、附件、索引、缓存、备份及重打包峰值列磁盘实际占用 |
| 资源收益 | 同机同条件配对，记录系统/架构、CPU/RAM、存储、工件与逻辑字节数、是否开模型、冷/热、样本量及波动。压缩级别、块大小、工作线程、读缓存每次只改一项 | 先过正确性硬约束，再看单位成本与延迟。候选以空间、CPU、延迟各自的改变量报告。高档若没有可见空间收益，保留已有表示；前台预算被压占时暂停后台任务 |

回填时前台只做授权、证据持久接受与短事务，模型和重打包走持久待办。确定性声明在事务内裁决。进程空闲时工作线程等待持久队列的下一次到期时间，CLI 短命令不加载模型、浏览器或整库索引。SQLite WAL 允许读写并行，仍只有一个活动写者。按页适度批量提交、限制单个读快照时间并观测 checkpoint 和 WAL 增长，防止一次回填影响前台交接。操作系统有文件缓存，初期优先复用 SQLite 页缓存与有界解码缓冲。以首个参考硬件上的数据模式测量作为基线，三平台端到端测完再发布性能数值。[SQLite WAL 并发与检查点](https://www.sqlite.org/wal.html#concurrency)
