# Botinkit Memory 升级功能设计

2026-11-26 · 产品提案，供确定下一轮升级范围。使用场景中的项目、错误码和测试输入为合成示例。引用的既有实测和公开研究均标明出处。

配套[技术设计](memory-upgrade-technical/README.md)给出七项功能的落点、接口与迁移、开源组件选型，以及自建 Harness 的接入和验证方式。

后续社区项目的采集、提炼、存储、淘汰和自进化算法如何独立试用、复现和替换，见[社区记忆算法接入设计](memory-upgrade-technical/community-integration.md)。

**建议首版解决两件每天会遇到的事。** 第一，用户改了一条工作约定，能立即知道它对哪个项目生效，换助手后也不用再说一遍。第二，用户说“接着昨天的排查”，新助手能指出上次做到哪一步、后来变了什么、下一步有什么依据。首版走通这两条路径后，再根据漏记、漏检或错用发生的位置决定投资。

| 建议顺序 | 用户可以做的新事情 |
|---|---|
| 首版 | 试算一条工作约定；换助手后，从上次有证据的步骤继续 |
| 第二批 | 查一次导入产出了哪些可用记忆；用错误码或另一种说法找到同一次检查；预演收窄权限后的结果 |
| 第三批 | 在新的版本上查看旧方法何时适用、何时失败；把一次错用纳入后续版本的回归评测 |

## 为谁解决什么问题

| 使用者与时刻 | 今天怎么做，代价在哪里 | 升级后的价值 |
|---|---|---|
| 同一位开发者，从 Claude Code 切到 Codex，或隔天重开会话 | 复制项目说明、重述偏好、翻昨天的终端输出。交接摘要可能把“准备复验”写成“已经通过” | 只交办任务，由助手取得适用约定和最近一次验证结果。用户能从每条结论点回获准的原句或工具回执 |
| 同一位所有者，在飞书讨论与多个开发会话之间整理依据 | 按时间回填后仍要判断哪条是原决定、哪条是转述。群内材料可供本人查阅，交给其他助手时还要逐段裁剪 | 导入完成即可知道新增了哪些依据、哪部分尚未处理。改变分享范围前，可试算指定助手下一次能看到什么 |

**已有基础。** V2 有按账号、对象、时间导入的入口，有声明修订、采集与提炼的独立授权、词法和向量搜索、撤回与宿主回执。上一轮用已有 release 验证，同样在声明入口输入“全局报告用中文”会生效，“今后所有代码示例使用 Rust”会停在待归并；当前确定性解析覆盖报告语言和开头。两款真实宿主已有通过 hook 与回环模型端点的测试，日常任务的采用与成功仍要单独核验。下文沿用 V2 的 F01–F12 来标识原有功能，方案获选后再进入项目规格和任务台账。[项目实测](landscape-2026-11-26/project-baseline.md) · [V2 功能索引](../docs/v2/product/README.md) · [已执行的验证](../specs/004-bmem-v2/validation.md)

## 七项升级如何定义

### 1. 让工作约定可以试算

**为什么升级。** “已收到”无法告诉用户下个项目会采用什么。首版在现有两个报告维度之外，增加明确的“代码示例语言”，支持全局默认、项目例外、单次要求和带截止时间的声明。优先验证一个新维度从写入到真实宿主使用的全过程。新增维度时复用同一套反例。[声明与装入 F02/F03](../docs/v2/product/memory.md#f02) · [当前解析范围](landscape-2026-11-26/project-baseline.md)

**用户体验。** 所有者追加“以后代码示例用 Rust，项目青禾这周五结束前用 Python”。在“当前声明”选择项目和时间试算：青禾周五显示 Python、周六显示 Rust，其他项目始终显示 Rust；详情列出对应原话、范围、时区、起止时间和版本。试算只读。一次性的“这次用 Go”随任务结束而退出。宿主装入状态单独显示，助手自己的转述只能提供候选依据。

**验收。** 在两个助手和两个项目分别开新会话，只问“给个最小示例”，检查实际输入与产出语言。到期后回到默认，原有报告格式仍有效。明确但尚不支持的维度提示“已收录，此类约定暂不能自动生效”；缺条件的候选等待后续证据，已确定维度照常生效。日常纠正通过追加原话完成。

回执示例可以直接回答“为什么这个助手还没照做”。所有者查看青禾项目时看到：“周五前，代码示例用 Python。Codex 本次会话已装入；另一个客户端仅可查询，本次装入未知。”这项规则仍然有效。某次输出遵循与否，要沿该次输出或工具动作另行核对。这是与 Claude Code 两轮共创中收紧的一处定义：权威库的生效状态和每次会话的装入状态各自记录。

### 2. 从上次接手的位置继续

**为什么升级。** F04 已定义接手卡，重复接手时用户还要从完整时间线中找变化。旧回放中，438 道有消息标注的题有 369 道找全来源会话，只有 203 道把每个来源中带标注的首选消息送出。它测的是旧 Python 路径，提示新版应单验“交给助手的证据够不够”。[原始回放](reassessment-2026-11/local-evidence.md) · [现有接手卡 F04](../docs/v2/product/memory.md#f04) · [UTILMEM](https://aclanthology.org/2026.emnlp-main.1639/)

**用户体验。** 在新会话说“继续青禾的导入排查”。有该任务的上次装入记录时，卡片突出此后新增的决定、最后通过的检查、新出现的失败和待验证的动作。只有本次上下文能证明仍保有那份任务证据时，才可只交付变化。新会话、上下文压缩重建或缺凭证时，先送当前约定、仍在的阻塞与最后一次验证依据，再标出变化。用户可回看获准的完整时间线。缺少装入回执时显示“上次接手位置未知”，走完整摘要；任务重名时只展示有权区分的候选。

**验收。** Claude Code 留下一句“准备重跑”和一条“解析通过、写入超时”的工具输出。Codex 首次接手时列出两个检查的不同结果，并从写入步骤继续。它装入后新增“重试仍超时”，同一上下文再次接手时突出这次变化。随后在同一宿主另开空会话，检查实际输入仍有先前解析通过的依据、写入失败和新重试结果。同仓其他任务的成功回执不能替代本任务证据。缺失回执时明确写“执行结果未知”。分别核对服务提供、实际装入、采用证据及独立任务结果。

### 3. 导入后能查清哪些资料成了记忆

**为什么升级。** 现有历史导入解决了“选哪些资料”和“读到哪里”。用户还需要知道成功导入的资料中，有多少真正形成了可供下次接手的依据。Hindsight 公开文档给出一个直接反例：原文已存、提炼产出零条事实，普通问答仍找不到它。[现有来源授权 F01](../docs/v2/product/governance.md#f01) · [开源项目的零事实案例](landscape-2026-11-26/open-source.md)

**用户体验。** 所有者选一次飞书群讨论、关联文档和两段开发会话的对象与日期。导入结果分别显示选中的源对象、已采集版本，以及每个版本的提炼去向，包括等待、未授权提炼、处理失败、处理后零候选、有候选及裁定结果。点击一条约定可看获准的原始发布、转述和独立回执。无法证明同源时显示“来源关系未确定”。源会变化或离线时标出仍可回查的版本与缺口；历史导入沿用现有所有者预览确认流程。

**验收。** 同一决定由两个助手转述，原生版本重复导入一次。可核实的转述链只算一个独立依据，重导不增加对应版本；后来独立执行的工具回执保留为另一项。暂停提炼时可见“已采集、等待处理”，恢复后只处理仍获准的版本。零候选可查原因或查看获准原文。一次性导入结束后，持续采集的开关按原设置工作。[采集与提炼的两条路径](landscape-2026-11-26/engineering.md) · [Agent 导入请求与所有者边界](../specs/005-agent-mcp-interface/spec.md)

### 4. 用错误码找原句，用改写找同一故障

**为什么升级。** 现有所有者搜索在词法、向量之间选一路。若先用语义限定候选，再给关键词加分，精确命中的记录可能永远没有机会入选。上轮在 Mem0 的固定版本复现了这一点，Hindsight 则演示了各路线候选可以独立进入合并池。[本地检索路径](landscape-2026-11-26/project-baseline.md) · [排序函数复核](landscape-2026-11-26/open-source.md)

**用户体验。** 搜索合成错误码 `E417` 时能看到对应版本、命中原句和同一次运行的结果。改问“写入阶段总是超时”时，开启向量的实例可将词法和语义候选合并，说明结果是按编号还是按语义找到。所有者搜索按本人权限返回；助手接手还需任务、来源、用途与实际接收端都获准。两条路径分别裁剪候选，补读时再次核对可见范围和剩余阅读预算。向量关闭或不可用时精确查询仍可完成。附近只有计划时，只呈现计划和证据缺口。

**验收。** 准备关键词独有、同义改写独有、同码不同项目、无答案四类题。固定候选总数和阅读预算，先比词法、向量与两路并集，再固定候选比较是否补读相邻结果。分别记目标原句是否找到、送入助手的依据是否充分、最后任务是否做对。两个项目都有同码时，撤去接手助手对其中一个来源的读取权。核对所有者仍可检索该来源，助手的实际输入只含另一项获准记录。仅当错失发生在跨实体关系且能标注每一跳时，再比较时态图能额外答对哪些题。[GrepMem 原文检索实验](https://arxiv.org/html/2611.25123v1) · [既有关系阅读 F10](../docs/v2/product/memory.md#f10)

### 5. 改变使用范围前，试算两个助手会看到什么

**为什么升级。** 用户可能只想让一段旧经历少出现，也可能想撤掉一个助手的访问权或要求遗忘。一个“删除”按钮无法表达这些意图。现有治理已有影响预览，新特性让所有者用**同一道问题**在变更前后比较两个接收者的可见结果。TimlMemBench 的 781 道激活题中有 774 道同时列出应使用与应避开的项目，适合测试这类取舍。[双语数据复算](landscape-2026-11-26/engineering.md) · [既有撤回与恢复 F06/F07](../docs/v2/product/governance.md#f06)

| 所有者的意图 | 可预期的结果 |
|---|---|
| “这段排查很少用，平时别主动带上” | 经历退出默认交接，获准的定向查询仍能找到。低频本身不改变事实效力 |
| “只到周五有效”或“我改主意了” | 按适用期或新修订取当前值；获准的历史查询仍可解释当时采用的版本 |
| “这个助手以后别读这段讨论” | 收窄该接收端的访问，新查询、旧句柄、待交付证据包按现授权检查。其他独立获准的材料继续可用 |
| “忘掉这次讨论” | 沿根来源标记受影响的原文和派生物。仅依赖该来源的摘要退出读取；有独立且充分的依据时可重建。已发副本、受管清理、备份可证明的截止点分别显示 |

**验收。** 从同一可读快照分别执行四种动作，检查受限项和仍应可读的一项。预览不改实际权限；确认撤权后检查旧句柄、重新导入和恢复预览。接收助手取得的任务包只带允许内容，屏蔽项的标题、摘要和数量不作为解释发给它。所有者只能在本人当前权限内检查差异。现有实现仅验证到恢复预览，实际恢复开放另按 F07 验收。[来源依赖与失效范围的实验](https://arxiv.org/html/2611.18133v1)

### 6. 把多次排查提炼成带反例的方法

**为什么升级。** 一次成功可以帮助交接，却不足以回答“这次也应该这么做吗”。V2 已规划跨案例归纳；这次新增用户可用当前工件版本查看适用性，并直接看到让建议失效的那个案例。重复出现的规则有时会把遗漏前提也一同放大。[自动提炼与方法归纳 F09](../docs/v2/product/memory.md#f09) · [执行轨迹归纳研究](https://arxiv.org/html/2611.26361v1)

**用户体验与验收。** 用户在新任务问“上次怎么修的，这次还能用吗？”青禾 v1 有两次独立验证，v2 有一次相同做法失败。助手显示“v1 两次验证通过；v2 有失败记录”，附前提、回执与反例。查 v2 时先给失败条件和待验证步骤；版本未知时保留不确定性。把同一份总结复制到另一个会话，独立案例数不增加；撤去唯一支持某一前提的来源，该建议停止主动出现，其他有效方法照常可用。

### 7. 把一次纠错变成下版可重放的用例

**为什么升级。** “这条是另一个项目的”可以立即纠正当前使用，也可以暴露整个检索策略的缺陷。现有回执能记录采用和结果，还需要一种低负担的方式，让所有者知道同类错误在候选版本中有没有再发生。[反馈与发布 F11/F12](../docs/v2/product/feedback.md) · [编码任务上的记忆对照](https://arxiv.org/abs/2609.23570)

**用户体验与验收。** 用户在错误的交接项旁指出“错项目”，必要时追加正确声明。当前纠正立即走原有流程。有评测用途授权时，从该错误形成用例，记录任务、应出现的证据、禁止出现的证据和判定方法。相同错误按根来源归组。新策略回放时显示“修复了哪题、原来正确的哪题退化、成本如何变化”。关闭学习许可后仍能纠错；仅获准日常读取的样本不进入评测或训练。回退排序或提炼策略后，用户刚纠正的有效声明仍为现值。

## 怎样排期与决定发布

下表是建议的三个交付批次。V2 原有授权、撤回、真实双宿主接手及基础提炼验收继续适用。每批复用现有 CLI 和本机 Web 的业务入口；同一声明、范围试算或治理操作在两端得到相同判断。只有所有者能作的控制动作继续留在所有者入口。[已有验收脚本](../docs/v2/product/acceptance.md) · [工作台入口](../docs/v2/ui/README.md)

| 批次 | 交付范围与依赖 | 进入下一步的依据 |
|---|---|---|
| 一 · 先让两款助手接得住 | 完成特性 1、2 的日常路径。复用已有来源导入、真实提炼、精确／词法查询与撤回。先覆盖声明三种明确维度，再把普通会话中的计划与同次运行的工具回执装进接手摘要，确保第一批就能交付这组必要证据，同时检查特性 5 的授权边界 | 两款真实宿主在新会话、压缩或重连后拿到适用声明。换宿主能从正确的失败步骤继续。例外到期、计划误报成功、同仓串题、撤权后泄露等预先写好的断言逐项通过；无装入凭证的个案单列为未知 |
| 二 · 补足取证和使用范围 | 交付特性 3、5 的所有者界面；将第一批围绕单次任务的补读，推广到特性 4 的通用错误码搜索和邻近结果。根据第一批的漏检样本比较两路并集，向量沿用用户开关。记录首次接手和再次接手分别节省了几次人工翻找 | 在同一授权语料、读者和阅读预算下，目标任务补回了确实缺失的证据，撤回后禁止项不可见，合法对照仍可用。在开发集选策略后另用时间留出集核验，再决定启用范围 |
| 三 · 有积累后才做长期优化 | 交付特性 6、7。前者需要有独立来源和版本差异的案例，后者需要可核验的任务结果与相应用途授权。图检索只试已证明缺关系证据的题型；训练须另有训练用途授权 | 配对结果能解释哪些任务获益、哪些退化，并有可回退版本。样本不足时保留单次经历和失败个案，继续积累证据 |

**衡量成败。** 首版记录三个结果：① 正确生效且范围、时间无误的必记项／已标注必记项，同时单列把临时要求误升为长期偏好的次数；② 最终输入含全部必要证据的任务／有授权且有充分证据的任务，同时检查无答案题是否乱用旧记忆；③ 无需用户补背景且独立验证完成的接手任务／全部接手任务。缺回执记未知并报告比例。重复提供背景的轮数、后台从采集到可用的等待时间、查询 p95 和每成功任务成本用于解释取舍。

**如何判断改动带来了收益。** 对同一任务固定宿主、版本、工具与阅读预算，比较关闭记忆、等长无关片段、系统自动证据、直接提供标注证据四组。按根来源和任务族做时间留出，分别报每款宿主新增成功和原先成功现失败的任务，区间不足以判断时保留现行策略。第一批试用前登记任务切片、最小有用收益和资源预算；当前调研没有真实日常流量的收益基线。[既有评测协议](reassessment-2026-11/evaluation.md) · [写入与检索组合研究](https://arxiv.org/html/2611.30230v1)
