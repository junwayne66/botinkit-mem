# 记忆系统升级评测样本与验收用例

七项产品特性使用同一套验收口径。每条 JSON 记录是一条独立用例，包含可重建的合成样本、操作步骤、观察位置和预期结果。另设社区算法接入测试，以及穿过多个功能的端到端测试。目录中的 F01–F07 对应升级 PRD 的第 1–7 项，X01 和 E2E 单独计数。[产品定义](../../PRD-memory-upgrade.md) · [数据与接口契约](../contracts.md) · [社区算法接入设计](../community-integration.md)

**合计 134 条用例、652 条断言。** 七项产品特性共 116 条，每项 16–18 条。社区算法与兼容性 15 条，跨功能端到端 3 条。

已记录本机安装版 bmem 0.2.0 的逐例判定、阻塞原因和复跑方式。[升级前基线报告](baseline-2026-11-27.md)

Spec Kit 006 的升级候选使用同一套样本。报告列出九组状态变化、整例观测与当前阻塞。[升级前后对比](comparison-2026-11-27.md) · [逐例 JSON](comparison-2026-11-27.json)

最终复跑使用同一候选二进制通过 134 条原样本和 652 条断言。9 个样本文件的哈希与升级前基线一致。[最终对比](final-comparison-2026-11-27.md) · [逐例结果与版本哈希](final-comparison-2026-11-27.json)

## 一条用例怎样执行

| 字段 | 执行约定 |
|---|---|
| `fixture` | 每例用新的临时数据根。原文、角色、版本、身份、授权和时钟取自本例。通过正常入口准备领域状态。注明“旧格式”的夹具用隔离的旧格式库。明确提供的旧回执、冻结日志、候选服务响应可作为待测环节的输入 |
| `steps` | 按数组顺序执行，使用给定读者、任务、会话与路由。形如 `@step`、`preview_step` 的引用从上一步真实响应解析。样本短 ID 映射到本次创建的真实 ID。工作目录、工具产物与两款宿主的执行账号均用合成测试环境 |
| `checks.at` 与 `path` | 在指定步骤的实际观测中按 JSON Pointer 定位。观测字段是测试适配器提供的投影，例如从真正发出的模型请求提取 `actual_input_text`，或将真实返回的修订按维度索引。记录原始响应、模型调用及工件的位置，使每个投影都可核查 |
| `op` | `eq` 比较 JSON 值，数组顺序参与比较。`contains` 和 `excludes` 对数组检查完整元素，对字符串检查子串。`absent` 要求父容器实际存在而目标字段缺失。缺少观测不能证明屏蔽有效 |
| `covers` | 可检索的场景标签。每条用例只计数一次，附带的反例、多读者、重复运行和断言数均不增加样本数 |

**例 · 第 51 条工具回执。** F02-09 把早期任务活动和最新失败放进同一时间线，检查被送到模型的任务包是否保留最后一次真实检查。若搜索能找到错误码，但最终模型输入只收到“准备重跑”，这条证据交付断言就应失败。F04-15 进一步区分“已经装入正确证据”和“独立任务验证通过”。

**观察能力。** 真实宿主用例通过启用 hook 的 Claude Code/Codex 发起调用，从隔离的模型入口抓取实际请求。任务成功以测试工件、执行回执或独立验证身份判定。宿主不可用时整例记 `NOT_RUN`。产品正常返回“结果未知”是某些用例要验证的业务结果，对应步骤仍需采到真实观测。可复用仓库已有的[宿主测试工具](../../../tests/v2/native_hosts.py)、[宿主集成测试](../../../tests/v2/test_native_hosts.py)和[隔离服务测试工具](../../../tests/v2/test_integration.py)。

## 校验、列举与判分

以下命令在本目录执行。评分器只依赖 Python 3 标准库。默认命令检查用例格式、每个特性的数量、步骤引用和断言约束。`--list` 同时列出每条用例的名称与覆盖标签。

```sh
python3 score.py
python3 score.py --group F05 --list
python3 score.py --case X01-01 --observations observations/hindsight.json
```

最后一条命令可直接复核已有的真实观测。X01-01 调用了 Hindsight 固定提交的融合函数，并和独立公式比较四组输入。观测文件保留原始标准输出，便于核对同分时的差异。[实跑观测](observations/hindsight.json) · [锁定源码、哈希与重放命令](../replay-example.md)

产品实现就绪后，执行器按用例操作并输出 `{用例ID: {步骤ID: 观测对象}}`。每个已执行步骤都需有观测对象。没有业务字段需要断言的准备步骤也应保留受理 ID、状态或审计引用。评分时只给执行器 `fixture` 和 `steps`，让评分器另读 `checks`。下列命令会逐条显示失败的步骤与字段。

```sh
python3 score.py --group F02 --observations /path/to/host-observations.json
python3 score.py --observations /path/to/all-observations.json
```

| 判分状态 | 含义 |
|---|---|
| `VALID` | 用例目录结构通过检查，尚未读取产品观测 |
| `PASS` | 本次所选用例的每步均有观测，全部断言满足 |
| `FAIL` | 该例有记录，但缺步骤、字段类型不符或观察值与断言不符 |
| `NOT_RUN` | 本次观测中没有这条用例。汇总保留它，不计通过 |

全体所选用例通过时判分退出码为 0，存在失败或未执行为 1，输入或目录无效为 2。样本中的延迟、费用、准入门槛和模拟时间只用于复算该场景。产品上线预算需要另用获准的日常任务测定。
