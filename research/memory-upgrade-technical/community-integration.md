# 社区记忆算法如何接入与复现

**新项目先作为一个可对照的实现进入实验。** 如果收益来自采集、归并、淘汰或自进化中的某一步，只接这一步。能独立替换的条件是输入、输出和写入权限都说得清，并且撤掉它后原有实现仍能处理下一次请求。这是拟议的开发方式，现有 Rust 服务还没有通用插件加载器。[架构总览与决策图](README.md#替换一个组件要改什么) · [已有扩展契约](../../docs/v2/technical/extension-contract.md)

## 收到一个新仓库，先决定怎样使用

| 上游提供什么 | 最短验证路径 | 采用后影响范围 |
|---|---|---|
| 可以独立调用的算法库 | 固定提交、许可与依赖，直接运行上游测试或示例，再用同一组输入验证本地类型转换 | 一个域内的适配实现、配置选择与契约测试。运行时适合 Rust 时可随制品编译 |
| 有独立 API 的 Python、Go 或其他服务 | 先用离线批处理或该服务原有协议收发获准输入与类型化结果。只有需要在线调用才维护外部进程 | 所属域承担限时、版本及失败回退。上游专用 ID、数据库和依赖留在适配器内 |
| 有论文、公式或源码，但依赖太重或协议不同 | 锁定论文版本，写出输入、步骤、参数和预期输出。优先用作者实现或已发布样例做对照，再做最小本地复现 | 复现代码及其对照夹具留在所属域。记录刻意改变的行为；只有论文而无可比实现时，结论限于“按描述复现” |
| 写入、检索和自我更新紧耦合的整套系统 | 用隔离数据根，从相同起点顺序投喂相同事件、修改、撤回与查询。对比现行 bmem、完整上游和只替换一个环节的 bmem | 完整系统先作实验基准。若只有多环节组合有效，再明确组合接口及共同迁移的状态。只有答案文本、缺证据来源时，仅比较任务结果 |
| 要求改变“什么事实生效”、授权语义或正式数据库 | 单列需要改变的不变量和受影响调用者。在副本上演练迁移，并保留旧格式及语义的对照 | 涉及核心用例、数据版本和迁移。按下文的存储边界评审 |

## 各环节交给社区实现的边界

| 可以试什么 | 给它什么 → 它交回什么 | bmem 保留的职责与最小反例 |
|---|---|---|
| D1 采集、切分、去重 | 原生分页/变更流 → 对象、版本、说话者和游标；原文版本 → 分段引用或相似来源对 | 保存页与游标、校验片段能回指原文。重复投同一页只受理一次，两次独立运行即使文字完全相同也各有根。新算法的游标与旧实现不兼容时从已对账的共同边界回放 |
| D3 提炼、归并、巩固 | 获准的版本片段、同域候选和时刻 → 带出处的事实、合并、冲突或方法候选 | D2 在现行授权下裁定，区分纠正、转述与独立观察。一次“这次用 Go”不得晋升为长期全局约定 |
| D4 存储组织、索引、检索与组包 | 已提交且仍可投影的记录 → 分块、时态边或索引；查询及可见域 → 候选片段、路径或有预算的选段 | 保存来源映射和处理到的版本。组包按本次读者回查正文。图里撤掉一条必要边时对应路径失效，另有独立依据的路径继续可查 |
| D4/D6 淘汰、冷热分层和压缩 | 允许使用的时间、访问记录和大小 → 冷热级别、默认优先级或可回查的压缩表示 | 明确纠正、访问控制、实际遗忘由本地治理提交。低频但有效的工作约定仍生效，冷资料仍能按原句定向找回；算法建议物理删除时转所有者治理流程 |
| D3/D2 记忆内容自进化 | 新证据与当前可读的旧案例 → 带支持、反例与适用版本的修订提案 | 保存父版本和原文，逐项裁定。对旧方法新增一个 v2 失败案例后，v1 的成功记录仍可按原版本查到 |
| D5/D6 策略自进化 | 获准的历史尝试、独立结果和冻结任务集 → 新归并规则、排序参数或策略工件 | 候选只在相同任务、预算、读者下比较，发布和回退按域记录。线上纠错独立生效，评测用途撤回时可追到受影响的工件 |

### 一个组件实际要改几处

假设要试一种**按反例更新旧方法适用范围**的社区算法。建议开发者按下表分工。表内为拟议挂接点，函数链接指向现有起点。

| 位置 | 本次需要做什么 |
|---|---|
| 实验输入输出 | 先冻结一段合成事件序列，含两个 v1 成功案例、一个 v2 失败案例和一次撤回。记录版本、到达顺序、预期出现和禁止出现的结论 |
| 算法实现 | 在 D3 做一个适配器，把当前新证据和允许读取的旧案例转成上游格式。返回目标方法版本、建议的新适用范围、支持与反例引用。可以先运行在临时进程中 |
| 接入选择 | 第一次试验用离线调用。进入产品时由 D3 在同一任务入口选择现行或候选实现，按已有 worker 的领取、授权复核和完成步骤运行。等两种实现都存在，再抽共用 Rust 接口。[待办领取与完成](../../src/v2/bmem/src/ingestion.rs) |
| 权威提交 | D2 根据候选和当前证据决定是否追加派生修订。今天的裁决器处理的是来源片段上的有限观察，承载方法版本、反例和依赖需要先实现 PRD 特性 6。完成这次共用契约后，下一个同类演化算法只需提供候选。[当前裁决](../../src/v2/bmem/src/authority.rs) · [拟增方法契约](contracts.md) |
| 宿主和退出 | Harness 继续使用同一接手请求与回执。关闭算法后停止接受它的新提案，已裁定事实按版本和依赖继续治理。需要纠正历史误判时追加有据修订；切回算法和撤销事实是两个有不同审计轨迹的动作 |

## 实例：把 A-MEM 的邻居更新拆出来

A-MEM 在加入新笔记时查找相关旧笔记，再决定建立连接或更新邻居的上下文和标签。固定版 `add_note` 同时调用 `process_memory` 并写检索存储，适合先拆出“怎样提出更新”进行验证。[论文](https://arxiv.org/abs/2502.12110v11) · [作者实现及固定提交](https://github.com/agiresearch/A-mem/blob/ceffb860f0712bbae97b184d440df62bc910ca8d/agentic_memory/memory_system.py) · [MIT 许可](https://github.com/agiresearch/A-mem/blob/ceffb860f0712bbae97b184d440df62bc910ca8d/LICENSE)

**固定版行为实测。** 用两组合成笔记执行上游的 `MemoryNote`、`find_related_memories` 和 `process_memory`。两次都固定检索返回 B、模型选择 `update_neighbor`，并将新上下文指定为 `write-timeout`。唯一改变的是内存中字典的初始内容与顺序。

| 初始笔记顺序 | 检索返回 | 实际被更新 | B 的结果 |
|---|---|---|---|
| B | B | B | `write-timeout` |
| A、B | B | A | 保留 `baseline-B` |

在此固定提交中，邻居查找传出的是结果中的位置，更新代码用该位置访问内存字典的顺序。两次运行的演化标志均为真，单看成功标志发现不了错项。由此得到一个具体接入条件：适配器须按检索结果的稳定 ID 绑定目标版本，在提交前核对目标仍有效，并对“结果名次与对象位置不同”保留回归样例。此实验替换了 Chroma 检索和模型回复，仅验证内存状态变化。源文件 SHA-256 为 `fa58c3ed405e37d298a3d11e5cd69459bc9709004461c0e01fc0c497c77c949b`。[邻居查找实现](https://github.com/agiresearch/A-mem/blob/ceffb860f0712bbae97b184d440df62bc910ca8d/agentic_memory/memory_system.py#L280-L320) · [更新实现](https://github.com/agiresearch/A-mem/blob/ceffb860f0712bbae97b184d440df62bc910ca8d/agentic_memory/memory_system.py#L684-L716)

| 同一次试验 | 观察或判断 |
|---|---|
| 固定邻居集合 | 保留上游选择的笔记和顺序，同时映射到本地 `event_id/span_id`。位置索引只能在本次调用使用 |
| 对照两种写法 | 隔离运行时可以让上游改自己的旧笔记。bmem 适配则采集修改前后的差异，变成“哪个派生版本、建议改什么、依据来自哪里”的提案。无法证明的依据记为待核 |
| 测出收益来自哪一步 | 固定相同的邻居、生成条件与阅读预算，对比关闭演化和开启演化。随后改变邻居选择单独比较。观察版本适用性判断、错改次数和额外成本。作者整套系统的论文成绩与本地适配分别记录 |
| 反例和回退 | 加入 v2 超时回执应收窄建议范围。把该回执原样转发不会增加独立案例数。撤回唯一的 v2 依据后，暂停依赖它的说明；用仍获准的证据重算，保留可追溯修订 |

## 存储替换的两种成本

| 目标 | 要做的工作 | 何时可以退回 |
|---|---|---|
| 试新的图存储、向量索引、冷热表或压缩布局 | 从获准权威快照派生。保存稳定来源映射、算法版本及可读水位，续跑增量和撤回。读之前复验可见性。能完整重建时，工程影响可以限在所属模块 | 关闭该读通道或选回已追平的旧投影。旧副本滞后时走现行可用路径 |
| 更换正式事实、授权与回执的数据库 | 当前采集事件、待办与游标共享事务，多域直接使用 `rusqlite`，治理和物理备份也依赖 SQLite。真要切换时按“接收一页、提交候选、治理提交、读取一致快照”等业务事务适配。先停写并排空在途作业，逻辑迁移稳定 ID、版本依赖、游标、幂等回执、授权、墓碑和必要运行状态，重建派生索引，对照源/目标后只开放一个写端 | 目标尚未接受新写时可切回原库。产生新写后必须先把增量、纠正和撤回追平并复核，再回切。用旧快照直接回退会复活已撤资料 |

## 怎样让下一次引入更快

每个候选只留一份可重跑记录。首次可随实验脚本和现有测试夹具保存，无需建设插件市场或新的任务平台。

| 要留下什么 | 工程师下次如何复用 |
|---|---|
| 来自哪里 | 上游项目、提交或论文版本、许可、依赖锁定、复现命令、适用环节。照同一命令能重新生成一份结果 |
| 怎样重放 | 输入快照及许可、按序事件、模拟时间、初始化状态、算法参数、随机种子或模型配置。输入不得含查询时尚不可见的未来事件。两种实现从独立干净状态起跑 |
| 怎样判断 | 先对上游示例，再与 bmem 现行实现逐项对照。记录契约断言、效果提升与退化、预算及失败样例。非确定性算法按重复运行的结果分布比较；单次固定响应只能验证状态转换 |
| 怎样退出 | 写明本域选择实现的位置、组件自有状态、重建来源和降级方式。若改动蔓延到 Harness 协议、来源身份或权威写语义，标明具体原因并提升为契约变更 |

下面是拟议实验记录的字段示例。分别给域内契约、上游实现和有状态工件标版本，换一个库的小版本就能重跑原夹具。只有改变调用语义才需要调用方迁移。

```yaml
capability: neighbor_revision_proposal
contract_version: 1
upstream: agiresearch/A-mem@ceffb860f0712bbae97b184d440df62bc910ca8d
inputs: [new_evidence_ref, visible_neighbors_with_versions]
outputs: [target_ref, expected_version, proposed_changes, support_refs]
state: per_run
baseline: preserve_existing_note
fixture: fixed_neighbor_b_with_different_insertion_order
```

上线选择可以留在所属域，CLI、Web 和 Harness 继续调用原来那一个业务入口。同一契约下可切换实现版本。有状态算法另记工件格式和已处理到的输入版本，读不了旧格式时从权威记录重建，待新工件追平后再切换。

可先用已有例子试走这条路径。Hindsight 的固定版融合函数与独立公式复现在四组合成输入上完成了分数和顺序对照，文中给出源文件哈希、运行命令以及等分时的差异。它验证了接入方法的第一步，产品收益仍需项目任务评测。[可运行的对照实验](replay-example.md) · [其他候选及采用条件](reuse.md)
